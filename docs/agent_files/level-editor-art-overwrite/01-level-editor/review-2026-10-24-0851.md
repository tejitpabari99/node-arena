## Must-fix — unprotected status GET starts unbounded process work

**Location:** `apps/web/src/dev/editor-middleware.ts:163` (status handler at lines 160–165); supporting guard `apps/web/src/dev/editor-middleware.ts:47` and runner `tools/src/editor-finalize.ts:48–50`.

`GET /__editor/status` invokes `editorFinalizeStatus`, which executes a fresh `pnpm validate:content --base HEAD --format json` process tree per request. `checkEditorRequest` requires the editor header and exact same Origin only for POST. The status route reads a job-gate snapshot but does not acquire/coalesce status work. Multiple concurrent simple GET requests pass the idle snapshot check and independently start validation.

A hostile page can send simple GET requests to the loopback endpoint without the POST Origin/header protection and cause unbounded process trees. Loopback Host validation does not prevent that browser request pattern. Revision checks after completion prevent stale publication, but do not bound resource consumption.

**Required fix:** make status a protected POST using the existing exact-Origin/editor-header policy; use a coalesced, revision-aware runner so concurrent requests share bounded status work and stale results are not published.
